# CI and workflow security hardening

This change adds three new GitHub Actions workflows (CI, dependency review, CodeQL scanning) and hardens the existing publish workflow by pinning all actions to full SHA hashes and fixing the pnpm version to `9` instead of `latest`. The publish workflow correctly continues to use NPM trusted publishing via OIDC — no secrets or `NODE_AUTH_TOKEN` needed. All workflows follow least-privilege permissions.

**Watch for:** The pinned SHA versions are the latest within their *v4* major lines, but every action used here has a newer major version available (v5 or v6). These workflows are already outdated on arrival (confirmed). The publish workflow is missing `--frozen-lockfile` on its install step, creating a determinism gap with CI (confirmed).

## High-level view

The SHA-pinning strategy is sound but chose old major versions. `actions/checkout` is pinned to v4.3.1 while v6.0.2 exists. `actions/setup-node` is at v4.4.0 while v6.4.0 exists. `pnpm/action-setup` is at v4.4.0 while v6.0.8 exists. `actions/dependency-review-action` is at v4.9.0 while v5.0.0 exists. Only `github/codeql-action` at v3.35.5 is the actual latest. Pinning to SHA is the right practice, but pinning to older majors means missing features and eventually hitting end-of-support.

The publish workflow's install step runs `pnpm install` without `--frozen-lockfile`, while the CI workflow correctly uses it. The publish job could resolve different dependency versions than what CI tested.

The three new workflows are minimal and well-scoped. CodeQL includes a weekly schedule for ongoing scanning; dependency review only triggers on PRs where it has a comparison base.

## Action version pinning: correct practice, wrong versions

Every `uses:` reference across all four workflows is pinned to the same set of SHA hashes:

- `actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5` — v4.3.1, the latest v4 patch. But v4 is two major versions behind: current is v6.0.2 (`de0fac2e4500dabe0009e67214ff5f5447ce83dd`).
- `actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020` — v4.4.0, the latest v4. Current latest is v6.4.0.
- `pnpm/action-setup@fc06bc1257f339d1d5d8b3a19a8cae5388b55320` — v4.4.0. Current latest is v6.0.8.
- `actions/dependency-review-action@2031cfc080254a8a887f58cffee85186f0e49e48` — v4.9.0, the latest v4. v5.0.0 exists.
- `github/codeql-action@f411752efdf656cb71aa17b755b22c890960da1d` — v3.35.5, confirmed as the actual latest.

The version comments in the YAML are accurate for what's pinned (no hash/comment mismatch) — the issue is that v4 shouldn't be the target. Newer majors of `actions/checkout` and `actions/setup-node` include performance improvements and Node 20+ runner compatibility changes that this project would benefit from.

## Install determinism asymmetry

The CI workflow:
```yaml
- run: pnpm install --frozen-lockfile
```

The publish workflow:
```yaml
- name: Install dependencies
  run: pnpm install
```

The publish job builds and publishes whatever `pnpm install` resolves at publish time. If the lockfile has any slack or is not perfectly in sync with `package.json`, the published artifact could differ from what CI validated. This should be `pnpm install --frozen-lockfile` — if something's wrong with the lockfile, it's better to fail the publish than ship unexpected dependencies.

## CI matrix: Node 18 EOL

Node 18 enters end-of-life in April 2025. Once EOL, testing against it provides no signal and creates noise when Node 18-specific issues arise that won't be fixed upstream. Not blocking, but the matrix should be updated to replace 18 with a current release in the near term.
